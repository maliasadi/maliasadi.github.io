Study notes

Building software with AI, specs, and OpenSpec

A reading deck for later. It covers the main AI-era ways of building software, then spec-driven development and OpenSpec in detail.

Seven ways the sources actually describe

01

Vibe coding

See it, say it, run it, paste the error. The code is not what you edit.

The seventh is spec-driven development, which the second half of the deck walks through with OpenSpec. These are practices, and people mix them. Steve Yegge's March 2025 essay treats vibe coding as a stance (the AI writes) that can sit on top of chat or agents, not as a seventh sealed box.

01 · Vibe coding

Forget the code exists, and keep going

SVG · PNG

  • What. Andrej Karpathy, February 2025: fully give in to the vibes, embrace exponentials, and forget that the code even exists. He accepts all diffs and does not read them.
  • Example. A weekend UI experiment. You describe the screen, run it, and paste the stack trace back with no comment.
  • Tools named by the sources. Cursor, GitHub Copilot agent mode, Windsurf, and Bolt, in a 2025 study of vibe-coding sessions. CACM also names Replit.
  • Fits when the result can be thrown away. GitHub's September 2025 Spec Kit post: fine for quick prototypes, less reliable for serious applications and existing codebases.
Quote path: Communications of the ACM, John Delaney, 6 May 2025, quoting Karpathy's February 2025 post. The paper "Vibe coding: programming through conversation with artificial intelligence" (arXiv:2506.23253) quotes the same post, including "I Accept All always, I don't read the diffs anymore." That paper's own finding is more careful than the slogan: the sessions they studied still alternate prompting, rapid scanning, running the app, and manual edits. Expertise moves toward context, evaluation, and knowing when to take the keyboard back. Thoughtworks (Ken Mugrage, 5 November 2025) says the term was meant flippantly and that antipatterns showed up quickly, including complacency with generated code.

02 · Autocomplete

An AI pair programmer, one line at a time

SVG · PNG

  • What. GitHub introduced Copilot in 2021 as an "AI pair programmer": stay in the flow, less boilerplate. CACM: these assistants started as autocomplete, finishing lines you had begun to type.
  • Example. You are inside a function you already understand. The tool offers the next line. You accept it, or you keep typing.
  • Tools. GitHub Copilot is the one these sources name for this older mode. Later Copilot posts describe agent mode and a coding agent as newer, separate modes.
  • Fits when you want to stay the author of the file. Control stays high because every suggestion is a small, visible choice.
GitHub Blog, Tim Rogers, 25 June 2025 (updated 2 July 2025): "When we introduced GitHub Copilot in 2021 as an AI pair programmer…" CACM, 6 May 2025, describes the autocomplete generation and then the later natural-language tools (Cursor, Replit, Windsurf). The same CACM piece summarizes a field experiment of about 5,000 developers at Microsoft, Accenture, and a Fortune 100 company: developers using Copilot completions increased completed tasks by more than 25 percent; less-experienced developers gained about 27 to 39 percent, senior developers about 8 to 13 percent. That is that study, not a promise about every codebase. Do not treat later agent features as this same loop.

03 · Chat

Chat-oriented programming is iterative prompts

SVG · PNG

  • What. Steve Yegge's name for it is CHOP. Sourcegraph, July 2024: coding via iterative prompt refinement. You commission the change. You review. The assistant is the programmer.
  • Example. Ado Kukic's write-up: add a new model to the Cody VS Code extension by asking where models are defined, then using an in-editor edit command, then asking again if the diff is wrong.
  • Tools the sources name. Sourcegraph Cody in that article. Yegge, March 2025, names in-editor chat in Copilot, Cursor, Sourcegraph, and Windsurf.
  • Fits when one person can describe the change and check the reply. Kukic's point: familiarity with the code is what tells you the reply is wrong.
Sourcegraph, Ado Kukic, 27 July 2024, "Chat-oriented programming (CHOP) in action." He also says tests can act as a contract of correctness for generated code, which is the bridge to the TDD slide. Yegge, "Revenge of the junior developer," 22 March 2025, later folds chat into what many people call vibe coding, and separates it from agents because you rendezvous with a chat on every turn. His productivity multiples in that essay are his estimates. They are not cited on the slide.

04 · Agents

Delegate the task, then review the change

SVG · PNG

  • What. Anthropic, December 2024: agents are models that direct their own process and tool use. A later, simpler line: LLMs autonomously using tools in a loop. Workflows, by contrast, follow a path you wrote in advance.
  • Example. GitHub's coding agent: assign an issue, or ask from Copilot Chat. It opens a draft pull request, pushes commits, runs tests and linters if the repo has them, and tags you. Comment @copilot to send it around again.
  • Tools. Claude Code (Anthropic's agentic coding CLI). GitHub Copilot agent mode in the editor, and the cloud coding agent. Anthropic's own coding-agent example is SWE-bench tasks from a pull-request description.
  • Fits when the task is open-ended but checkable, and you trust the sandbox. Anthropic: higher cost, and errors can compound. Human review still has to judge fit with the rest of the system. GitHub: you stay in control, and the agent's pull requests need human approval before CI runs.
Anthropic, "Building effective agents," 19 December 2024. The page now notes that the tooling landscape has changed and points at Claude Managed Agents; the definitions above are from that post. Anthropic, "Effective context engineering," 29 September 2025, gives the shorter "tools in a loop" definition. Claude Code best practices, Boris Cherny, 18 April 2025: the tool is low-level and does not force one workflow. A community pattern on that page is explore, plan, code, commit, and steps 1 and 2 matter because otherwise it jumps straight to code. The post says it is no longer the maintained copy and points at https://code.claude.com/docs/en/best-practices . GitHub Blog coding-agent posts: "Meet the new coding agent," "From pair to peer" (25 June 2025), and "coding agent 101." Use those for the issue-to-draft-PR loop. Do not describe the agent as merging its own work.

05 · Tests first

AI-assisted TDD gives the agent a fixed target

SVG · PNG

  • What. Classic TDD, from Kent Beck via Martin Fowler: write a test, make it pass, refactor. Red, green, refactor. With an agent, someone still has to decide who writes the test.
  • Anthropic's loop for changes that tests can check: ask for tests from input and output pairs, run them and confirm they fail, commit the tests, then tell the agent to implement without modifying the tests until they pass.
  • Example. A parser with three awkward cases. You write those three failing tests yourself. The agent may only turn them green.
  • Fits when the behavior is statable as a test. Thoughtworks, February 2026: if the agent writes the test after the code, it can lock in its own bug. A human-written test is a target it cannot quietly move. Böckeler's exploratory runs found no clear quality win when the agent did the whole red-green loop by itself, on small greenfield tasks. She flags the sample as small.
Fowler, "Test Driven Development," updated 11 December 2023: the three steps, plus a list of tests you pick from. Original page 5 March 2005. Anthropic Claude Code best practices, section "Write tests, commit; code, iterate, commit." Thoughtworks, Ken Mugrage, "Where does the rigor go?", 20 February 2026. The "one practitioner" in that post is not named. Birgitta Böckeler, "TDD inside the agent loop," on martinfowler.com: three placements of TDD (human writes tests; human reviews the failing test; fully inside the agent). Her setup used Sonnet 4.6 to generate and Opus 4.8 to judge, greenfield business logic only, and she says none of the runs followed TDD perfectly. Do not quote her batches as a benchmark. Dan North, 20 September 2006, is on a later slide for BDD, which grew out of teaching TDD.

06 · Context

Context engineering curates the window

SVG · PNG

  • What. Anthropic, 29 September 2025: after prompt engineering, the question is which configuration of context is most likely to produce the behavior you want. Context is every token in the call, not only the prompt you typed.
  • The loop. Curate on every turn. Find the smallest high-signal set. For long tasks they describe compaction (summarize and restart), notes outside the window, and sub-agents that return a short result. Just-in-time fetch is slower than a precomputed index, and an agent can waste the window chasing dead ends.
  • Example. Claude Code loads CLAUDE.md up front and uses search to pull files only when it needs them, instead of pasting the repository into the prompt.
  • Fits when a session is long enough for the window to fill. Anthropic's name for the failure is context rot: as tokens grow, recall gets worse. Thoughtworks, November 2025: this is the shift they see after vibe coding, and humans still need the context too.
Anthropic engineering, "Effective context engineering for AI agents," 29 September 2025. Authors listed there: Prithvi Rajasekaran, Ethan Dixon, Carly Ryan, Jeremy Hadfield, and others. The n-squared attention point and the Goldilocks altitude for system prompts are in that post. Thoughtworks, Ken Mugrage, "From vibe coding to context engineering," 5 November 2025. He names agents.md, Context7, Mem0, and the Model Context Protocol as context-related technology, and says it remains to be seen which standards win. OpenSpec's README says the same hygiene in one line: clear the context before implementation. That is cited again on the OpenSpec slides.

07 · Specs

Spec-driven development writes the behavior first

SVG · PNG. The large version is two slides ahead.

  • What. GitHub, 2 September 2025: start from a spec, a contract for how the code should behave, and treat it as the source of truth for people and agents. Böckeler, 15 October 2025: a structured, behavior-oriented artifact, in natural language, that guides the agent. Not the same thing as a rules file.
  • Example. "Add photo sharing" is too thin. The spec says who shares, what success looks like, and what must not happen. The plan then names the stack. Tasks are small enough to review.
  • Tools. GitHub Spec Kit, OpenSpec, and Kiro. Compared in the second half.
  • Fits when the behavior has to stay specified after the chat scrollback is gone. OpenSpec's reason, from its README: assistants are unpredictable when requirements live only in chat history.
The five phase names on the diagram are the study loop used in this deck: Spec, Plan, Tasks, Implement, Verify, then back to the spec. GitHub's blog uses Specify, Plan, Tasks, Implement, and says your job at each phase is to verify. Spec Kit's current README adds a constitution up front and a converge step after implement. OpenSpec does not use these five names as five commands. The annotation on the diagram is the accurate mapping: propose drafts the proposal, delta specs, design when needed, and tasks together; apply implements; archive merges an accepted delta and is not the verify step. The verify command exists only on the expanded profile.

Control and reliability, as the sources describe them

Vibe coding Low on purpose. Karpathy accepts the diff and does not read it. "Mostly works." GitHub: weak for serious apps and existing systems. The code can outgrow your understanding.
Pair programming High. You see each suggestion and keep typing if it is wrong. You are still reading the line. This does not review a whole design.
Chat-oriented You accept or ask again. Kukic: you are the reviewer. You can only catch what you still understand. The model can be wrong in fluent prose.

Direction of travel

What the sources say is changing

GitHub · June 2025

From pair to peer

Copilot's own account moves from the 2021 pair programmer to agents that plan, edit, and test, with a person still able to interrupt.

Anthropic · 2024–2025

Simple first, then context

December 2024: start with a prompt, add an agent only when it beats the simple version. September 2025: curate context on every turn. Smarter models need less prescription. The window is still finite.

GitHub · Sept 2025

Intent as the source of truth

The Spec Kit post says specs become executable and code is the last mile. Böckeler, a month later: the word "spec" is already fuzzy, and sometimes people just mean a long prompt.

Thoughtworks · 2025–2026

Rigor moves. It does not vanish.

November 2025: from vibes toward context, and humans remain critical. February 2026: review effort moves toward specs, tests, types, risk, and ongoing understanding. Checking in English and deleting the code is not where they say we are.

These are dated claims from those pieces, not a forecast this deck is making. Yegge's March 2025 timeline for agent fleets is his prediction. It is not used here as a fact.

Hold these four cards against each other. GitHub is arguing that intent should drive generation. Böckeler is warning that the artifacts can become a second, worse review pile, and that spec-as-source resembles model-driven development with new failure modes: inflexibility plus non-determinism. Thoughtworks is arguing the review still has to land somewhere concrete. Anthropic is arguing against jumping to the most elaborate agent. A practical reading, labeled as a reading: use the lightest loop that still leaves a check you trust, and write something durable (a test, a spec, or both) when the change will be maintained.

Spec-driven development

Three depths, and they are not the same tool

Spec-first

Before this change

Write a spec, then use it for the task in front of you. Böckeler: every approach she found does at least this.

Spec-anchored

After the change too

Keep the spec and edit it when the feature changes. OpenSpec's archive step is built for this: deltas merge into openspec/specs.

Spec-as-source

People edit the spec only

The spec is the file you maintain. Code is generated and not hand-edited. Böckeler saw this explored in the Tessl Framework, then in private beta.

A spec, in her definition, is behavior for one feature. A memory bank, constitution, or CLAUDE.md is context for every session. Mixing the two is how a rules file gets treated as a specification.

Birgitta Böckeler, Understanding Spec-Driven-Development, 15 October 2025. She warns the tools were moving fast and her notes are from using them that September.

Do not update her Tessl status past October 2025. The article says the framework was in private beta, with a 1:1 spec-to-file mapping and a generated-from-spec comment, and that regenerating the same spec did not always produce the same code. Spec Kit, in her reading then, looked spec-first for the life of a change rather than spec-anchored for the life of a feature, because a spec lived on a branch. Spec Kit's current concepts page says the project does not prescribe how teams keep spec.md after requirements change. Kiro, in her reading, was spec-first inside its editor. Kiro's current docs are on the tooling slide. OpenSpec is the tool in this deck that documents a merge from change deltas back into a lasting specs directory.

The loop in words

Specify, plan, task, implement, verify, revise

  1. Spec. What and why. User journeys and outcomes, not the stack. GitHub: who uses it, what problem it solves, what success is.
  2. Plan. How. Stack, architecture, constraints, legacy systems, compliance. You can ask for more than one plan.
  3. Tasks. Small pieces you can implement and check. GitHub's example of the right size: "create a user registration endpoint that validates email format," not "build authentication."
  4. Implement. The agent does one task. You review that change, not a thousand-line dump.
  5. Verify. GitHub: your role is to verify, not only to steer. If the spec is wrong, change the spec and regenerate. Spec Kit's current flow ends this pass with /speckit-converge, and you repeat implement and converge until it reports Converged.

The September 2025 blog used the chat commands /specify, /plan, and /tasks. The current Spec Kit README uses /speckit-specify, /speckit-plan, /speckit-tasks, /speckit-implement, and /speckit-converge, invoked in the agent's chat, not the terminal. Install is now uv tool install specify-cli and specify init. The blog's install line was uvx from the git URL.

Blog: Den Delimarsky, GitHub Blog, 2 September 2025. Current commands: github/spec-kit README, fetched for this deck. The README also says to establish a constitution once, with /speckit-constitution, and that a longer path adds clarify, checklist, and analyze. Python 3.11+ and uv are the documented requirements. Copilot's default syntax is the slash form above. Other agents use a different spelling. See the integration page linked from the README rather than guessing. Beside older practices

TDD, BDD, prompting, and a spec

What you write first What "done" means
Plain prompting A chat message. GitHub's example of the failure mode is "add photo sharing to my app." Whatever the model assumed. You often find the wrong assumption late.
TDD An executable test, then code, then a refactor. Beck, via Fowler. The test list comes before the first red bar. The test passes, and the structure is cleaned up. Skipping the refactor is the usual way to do it badly.
BDD A sentence of behavior. North, 2006: he replaced the word "test" because it was the source of the confusion, and built JBehave around "should." The behavior you named is the one the system shows. Later he describes scenarios as givens, events, and outcomes, in the language of the business.
Spec-driven A natural-language behavior spec the agent and the human share, then a plan and tasks. The implementation matches the spec, and the spec is what you change when the intent changes.

OpenSpec scenarios are WHEN / THEN under a requirement that uses SHALL or MUST. Kiro's current requirements-first docs use EARS: WHEN … THE SYSTEM SHALL. Böckeler saw GIVEN / WHEN / THEN in Kiro in September 2025. Do not treat those as one format.

OpenSpec

A lightweight spec layer beside the code

OpenSpec is a spec framework from Fission. The README's philosophy:

  • fluid not rigid
  • iterative not waterfall
  • easy not complex
  • built for brownfield, not only greenfield
  • scalable from personal projects to enterprises

The concepts doc states the first four and explains them. Fluid means no phase gates. The README's matching line is that you can update any artifact at any time. Deltas exist so a change can describe a modification of a system you already have.

openspec/
├── config.yaml
├── specs/        # current behavior
│   └── auth/spec.md
└── changes/
    ├── add-dark-mode/
    │   ├── proposal.md
    │   ├── design.md
    │   ├── tasks.md
    │   └── specs/  # the delta
    └── archive/

specs/ is the source of truth. changes/ holds one folder per proposed change. Archive merges the delta and moves the folder. Layout from the setup and spec-driven schema docs.

README: https://github.com/Fission-AI/OpenSpec . Concepts: https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md . Setup: https://openspec.dev/docs/setup . Schema: https://openspec.dev/docs/schemas/spec-driven . config.yaml is project settings and context for the agent. Specs are organized by domain. The schema's drafting order is proposal first, then specs and design in either order, then tasks, then apply. Design can be omitted when none of its conditions apply. A change with no behavior change sets skip_specs: true in .openspec.yaml. openspec validate rejects a zero-delta change without that marker. Stores, marked beta in the README, are a separate planning repo with the same openspec shape, shared by git. The README contrasts OpenSpec with Spec Kit (heavier, rigid gates, Python) and with Kiro (it says locked to their IDE and Claude). Kiro's own docs now list IDE, CLI, and Web, so that lock-in sentence is OpenSpec's comparison, not Kiro's current capability list. The tooling slide uses each project's own docs.

Workflow

The default path, then the commands

Quickstart, in the agent's chat. The examples are plain language so they work across tools. A fresh chat for apply is recommended, because implementation goes better on a clean window.

  1. Explore, if the idea is still fuzzy. It reads the code and writes nothing unless you ask.
  2. Propose. Review the plan before any code.
  3. Apply. It checks off tasks.md. Ask again to resume at the first open box.
  4. Archive, once the boxes are checked. Specs absorb the change. The folder moves to changes/archive/.

Default profile core: explore, propose, apply, update, sync, archive. Expanded, after openspec config profile and openspec update: new, continue, ff, verify, bulk-archive, onboard.

openspec init --tools cursor
openspec new change add-dark-mode
openspec status --change add-dark-mode
openspec validate
openspec archive add-dark-mode -y

# canonical chat names
/opsx:propose add-dark-mode
/opsx:apply
/opsx:archive

Cursor spells the commands /opsx-propose and /opsx-apply. Claude Code uses the colon form. Codex uses $openspec-propose. The same workflows also install as skills, for example /openspec-apply-change. The skills page is the published list. The slash-command writeup lives in the repository.

Quickstart: https://openspec.dev/docs/quickstart . The five steps there are explore, propose, review, apply, archive. Review is you, reading proposal.md, then specs/, then tasks.md. CLI: https://openspec.dev/docs/cli . openspec new change creates only .openspec.yaml (schema and created date). Worked example

A change proposal, in the documented shape

Study text, written in the spec-driven template. It is not a file from the OpenSpec repository. The dark-mode story is the one in the README.

# Proposal

## Why
The app has a single theme. People using it at night have asked for a dark one.

## What Changes
- Add a theme control that follows the system preference until a person chooses.

## Capabilities
### New Capabilities
- ui: theme selection for the application shell

### Modified Capabilities

## Impact
Styling and a small piece of client state. No new dependency.

Template sections from the spec-driven schema: Why, What Changes, Capabilities, Impact. A capability name becomes specs/<capability-path>/spec.md. Implementation detail belongs in design.md, not here.

The schema says the Capabilities section is the contract with the specs phase. Before filling it in, the instructions say to run openspec list --specs, then openspec show for related specs. openspec list without --specs lists in-flight changes, not the capability inventory. New capabilities use kebab-case path segments. Modified capabilities must be existing paths whose requirements change, not merely whose code changes. Mark breaking changes with BREAKING in What Changes. Keep the proposal to about one or two pages.

Worked example

The delta spec for that change

# Spec Delta

## Purpose
Lets a person choose a light or dark theme and keep that choice on this device.

## ADDED Requirements

### Requirement: Theme selection
The app SHALL let users switch between light and dark themes,
defaulting to the system preference.

#### Scenario: User toggles dark mode
- **WHEN** the user clicks the theme toggle
- **THEN** the app switches to dark mode and persists the choice
  • The requirement sentence is the README's. The Purpose line is study text. A new capability wants a Purpose. Archive copies it into the new main spec. Skip it and the main spec is left with a TBD placeholder.
  • Other delta sections: MODIFIED (paste the whole requirement, then edit), REMOVED (include Reason and Migration), RENAMED (FROM / TO).
  • Scenarios use exactly four hashes. Three hashes fail silently. Every requirement needs at least one scenario. Normative lines use SHALL or MUST. openspec validate checks the structure. --strict also fails a requirement description over 500 characters, and a Purpose under 50.
Schema page and concepts page. WHEN / THEN is the template. The concepts page also shows GIVEN / WHEN / THEN / AND in an older-looking auth example. The schema template, which validate is written against, shows WHEN and THEN and four hashes. Teach the schema form. On archive: ADDED is appended, MODIFIED replaces the requirement whose header matches, REMOVED is deleted. Removing the last requirement retires the capability and deletes spec.md only if the change sets retire_capabilities: true. Otherwise archive aborts. A delta for an existing capability must not add a new Purpose. Edit the main spec's Purpose directly. The quickstart's archive pictures use add-rate-limiting and show the folder landing as archive/YYYY-MM-DD-add-rate-limiting. The CLI's worked transcript uses add-rate-limit and the same date-prefix pattern.

The whole change folder, delta included, moves under changes/archive/ with today's date prefixed to the name.

There is also /opsx:sync, whose documented job is to merge delta specs into the main specs. The CLI command openspec archive both updates the main specs and moves the folder. Git is separate: commit the change folder with the code.

OpenSpec does not prune the archive for you. You can delete an archived change's specs/ after the merge is committed, if Git is your history. openspec validate --archived checks task completion, not the applied deltas.

Judgment

When the spec is worth it, and when it is not

The sources say it helps

  • You and the agent agree before code. OpenSpec.
  • Greenfield work, a feature in a system that already exists, and a legacy rebuild where the original intent is gone. GitHub.
  • Brownfield edits, because a delta shows the change instead of restating the whole spec. OpenSpec concepts: two changes can touch one spec if they touch different requirements.
  • Security, compliance, and design-system rules have somewhere the agent will actually read. GitHub.

The sources say it hurts

  • A small bug. Böckeler's Kiro run turned one into 4 user stories and 16 acceptance criteria. She calls that a sledgehammer.
  • A modest feature with a pile of markdown. She would rather have reviewed the code, and an agent ignored research notes and regenerated classes that already existed.
  • A false sense of control. A longer context window does not mean the agent uses everything in it.
  • Spec-as-source, if it inherits model-driven development's overhead and the model's non-determinism together.

OpenSpec's documented escape for a refactor, tooling, or docs-only change with no behavior change: skip_specs: true. Do not invent a requirement so validation will pass.

Böckeler's conclusions: spec-first is valuable, the term is semantically diffused, and elaborate tools may be a Verschlimmbesserung, making something worse while trying to improve it. She also asks who the user of these workflows is. Demos assume a developer writes the user stories. That may be the wrong person for a large, unclear feature. GitHub's three scenarios are in the 2 September 2025 post. OpenSpec concepts, "Why Deltas Instead of Full Specs": clarity, fewer conflicts, review of the change rather than the unchanged text, and brownfield fit. skip_specs is in the schema instructions.

Start here

A checklist you can run this week

  1. Pick the lightest loop that still leaves a check. A line suggestion, a chat edit, an agent with a draft PR, a failing test, or a spec. Anthropic's December 2024 advice is to add machinery only when the simpler version is not enough.
  2. If the session will be long, write the context down. A short CLAUDE.md or the equivalent, not the whole repository pasted into the prompt.
  3. Install OpenSpec from the README: the binary installer, npm install -g @fission-ai/openspec@latest (Node.js 20.19.0 or newer), or brew install openspec.
  4. In the repo: openspec init --tools cursor (or claude, or the picker). Restart the editor.
  5. Explore, or /opsx:propose with a kebab-case name. On Cursor the command is /opsx-propose.
  6. Read proposal, specs, then tasks. Edit the markdown yourself if the agent missed a case. No code yet.
  7. New chat. Apply. If it stops, apply again. It resumes at the first unchecked task.
  8. openspec validate, then archive. Commit the spec with the code.
  9. For a pure refactor, set skip_specs: true instead of faking a requirement.
  10. Turn on the expanded profile only when you want /opsx:verify before archive.
Node version and install commands: OpenSpec README. Init flags: CLI page. Apply resume behavior and the fresh-chat advice: quickstart. skip_specs: schema page. Profile switch: slash-command page and setup page. Spec Kit, if you want that toolchain instead: uv tool install specify-cli, then specify init my-project --integration copilot, from the current README.
